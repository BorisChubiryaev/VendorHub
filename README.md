# ВендорХаб — MVP

Веб-приложение для регистрации потребностей в ИТ-ресурсах и подбора вариантов их обеспечения из бассейна кандидатов
(сценарий «MVP ВендорХаб.new (потребности + бассейн)»).

## Что реализовано

| Сценарий | Где в приложении |
|---|---|
| **1.1** Регистрация потребности: продукт (подсказки по продуктам трайба), ссылка на объект бэклога и summary требований, создание нового объекта бэклога, ролевой состав (роль, уровень, количество, навыки, даты в календаре), отправка на подбор / черновик / отмена. Инициатор и трайб — предзаполнены и не редактируются | «Новая потребность» |
| **1.2** Визард выбора способа обеспечения: сценарии «Лучшее совпадение», «Быстрый вывод», «Наименьший бюджет», «Свой сценарий»; по позиции — признак собеседования, карточка кандидата, ручной поиск замены (с преднастройкой фильтров), замена кандидата на запрос по договору; групповые действия (удаление, запуск на маршрут, перенос в новую потребность — split); статус обеспечения по маршруту | Карточка потребности |
| **1.3** Поиск и просмотр моих потребностей: ID, инициатор, продукт, дата начала (минимальная по позициям), состав и статус позиций | «Мои потребности» |
| **1.4** Карточка предложенного кандидата: ФИО, возраст, роль и уровень, навыки, рейтинг, интервал доступности, опыт, УВБ, город, ставка, опыт в Сбере, опыт по резюме, отзывы + релевантность и возможность привлечения | Карточка кандидата |
| **1.5** Все подобранные кандидаты под позицию: плитки / таблица, фильтры (доступность, роль, уровень, подрядчик, город, навыки, УВБ, рейтинг, ставка) | «Кандидаты», «Ручной поиск замены» |
| **1.6** Регистрация потребности через ассистента: диалог в свободной форме, уточнение недостающего, подтверждение, регистрация карточки (и, при необходимости, создание задачи в бэклоге) | «Ассистент», webhook СберЧата |
| **2.1** Регистрация и редактирование карточки кандидата (включая статус карточки и отзывы) | «Новый кандидат», «Редактировать» |
| **2.2** Импорт PDF-резюме: выбор нескольких файлов, построчный статус обработки, ID и ссылка на карточку в статусе «Черновик», список нераспознанных полей | «Импорт резюме» |
| **2.3** Поиск кандидатов для редактирования: статус, создатель, роль, уровень, подрядчик, город и др.; плитки / таблица | «Бассейн кандидатов» |

Общие параметры: локальная авторизация по логину и паролю (без СУДИР), backend и frontend поставляются одним контейнером.

### Логика подбора (схема «Варианты обеспечения позиций»)

Для каждой позиции фактической потребности (позиция с количеством N при отправке раскладывается на N позиций по одному человеку):

1. Ищутся активные кандидаты бассейна по роли и интервалу доступности. Если у вендора кандидата есть договор с этой ролью,
   покрывающий интервал позиции, и по договору есть лимит на интервал:
   **1** — лимит трайба заказчика → рекомендация кандидата; **2** — лимит другого трайба; **3** — лимит в резерве блока Т → «иди в закупки».
2. По реестру договоров ищутся договоры с ролью и покрытием интервала: **4** — лимит трайба заказчика → «иди к вендору»;
   **5** / **6** — лимит другого трайба / в резерве → «иди в закупки».
3. Иначе **7** — новый договор → «иди в закупки».

Релевантность кандидата (0–100): роль 30, навыки 30, уровень 20, покрытие интервала 15, рейтинг 5.
Сценарии строятся жадно по всем позициям, один кандидат не назначается на две позиции.

Маршруты по таблице сценариев: А (вариант 1), Б (2), В (3), Г (7), Д (4), Е (5), Ж (6) — шаги «подтверждение кандидатом»,
«собеседование» (если установлен признак), «передача лимита», «заявка на ресурс (ЗНР/ЗНРД)», «заключение договора».
При запуске позиций на маршрут потребность передаётся в штаб.

## Быстрый старт

Требуется Node.js ≥ 22.5 (используется встроенный `node:sqlite`).

```bash
npm install
npm run dev        # API на :3000, фронтенд на http://localhost:5173
```

Продакшн-сборка:

```bash
npm run build
npm start          # всё на http://localhost:3000
```

Docker (для размещения на стенде):

```bash
docker build -t vendorhub .
docker run -p 3000:3000 -v vendorhub-data:/data -e JWT_SECRET=... vendorhub
```

Настройки — переменные окружения, см. [.env.example](.env.example). В пустую базу автоматически загружаются демо-данные
(`SEED_DEMO_DATA=false` — отключить); пересоздать демо-базу: `npm run seed`.

### Демо-пользователи

| Логин / пароль | Роль |
|---|---|
| `customer` / `customer` | Заказчик ИТ-ресурсов, трайб «Розничный бизнес» |
| `customer2` / `customer2` | Заказчик, трайб «Корпоративный бизнес» |
| `manager` / `manager` | Менеджер бассейна |
| `admin` / `admin` | Обе роли (переключатель в меню) |

Демо-данные покрывают все варианты 1–7 для трайба «Розничный бизнес» (на интервал 01.12.2026–31.05.2027):
Frontend/QA → 1 и 4; Data Scientist, Data Engineer, Scrum-мастер → 2 и 5; аналитики, мобильная разработка, UX/UI → 3 и 6;
Fullstack и Архитектор → 4 (кандидатов в бассейне нет); Руководитель проекта → 7 (договоров нет).
Примеры резюме для импорта: [`server/test/fixtures/resume-*.pdf`](server/test/fixtures).

## Интеграции

| Система | В MVP |
|---|---|
| Jira / СберТрек | `BACKLOG_PROVIDER=jira` — REST API v2 (поиск, создание задачи, summary по ссылке); по умолчанию — встроенный бэклог |
| СберЧат | `POST /api/integrations/sberchat/webhook` (заголовок `X-Bot-Token`, тело `{chatId, userLogin, text}`) — тот же диалоговый движок, что и в веб-ассистенте; ответы возвращаются в теле и, если задан `SBERCHAT_OUTBOUND_URL`, отправляются туда |
| Языковая модель | `LLM_API_URL` — OpenAI-совместимый endpoint (например, шлюз к GigaChat): дополняет разбор реплик ассистента и резюме. Без неё работает разбор по правилам |
| Пульс, Пульс.Подбор, модуль лимитов, ЛК (ЗНР/ЗНРД), закупки, штаб | Исходящие сообщения журналируются (журнал интеграций на карточке потребности). Ответы систем — через `POST /api/integrations/callback` (`X-Integration-Token`, `{positionId, outcome: success|fail}`) или эмулятор на карточке потребности |

## Устройство

```
server/   Express 5 + TypeScript, SQLite (node:sqlite), JWT
  src/services/matching.ts      подбор вариантов 1–7, релевантность, сценарии
  src/services/routing.ts       маршруты А–Ж
  src/services/needs.ts         жизненный цикл потребности
  src/services/assistant/       диалоговый ассистент (NLU на правилах + LLM)
  src/services/resumeParser.ts  распознавание PDF-резюме
  src/services/backlog/         Jira / встроенный бэклог
web/      React 18 + Vite + TypeScript
```

Тесты: `npm test` (подбор и сценарии, маршруты, разбор текста, распознавание резюме, сквозные сценарии API).

## За рамками MVP

Анализ договорного состава и интеграция с CAP (лимиты / остатки бюджетов), сложные сценарии передачи лимитов,
СУДИР, справочник продуктов ЕКОУ, промышленная СУБД (слой доступа к данным изолирован в `server/src/db`).
